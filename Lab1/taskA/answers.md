**Окружение:** Linux x86-64, `g++ (GCC) 14.4.0` (Docker-образ `gcc:14`, `--platform linux/amd64`).

Все команды собраны в [run.sh](run.sh), их полный вывод — в [output.txt](output.txt).

## Этап 1. Препроцессинг (`simple.i`)

```bash
g++ -E simple.cpp -o simple.i
wc -l simple.cpp simple.i
```
```
   23 simple.cpp
 1100 simple.i
```

**1. Сколько строк было в исходном файле и сколько стало в `.i`?**

Было 23 строки, стало 1100 — примерно в 48 раз больше. 26 760 байт против 397.

**2. Что находится над `main` в `simple.i`? Почему там так много строк?**

```
$ grep -n 'int main' simple.i
1095:int main() {
```

Над `main` (строки 1–1094) лежит:

- **содержимое `<cstdio>` и всего, что он подключает** (`<stdio.h>`, `bits/types.h`, `stddef.h`, `stdarg.h`, `struct _IO_FILE`, `__gnuc_va_list` и т. д.). `#include` — это текстовая подстановка: препроцессор вставляет файл целиком и рекурсивно раскрывает его собственные `#include`. Поэтому в `.i` попадают объявления `printf`, `fopen`, `FILE`, `size_t` и ещё сотни сущностей, хотя нам нужна только `printf`:
  ```
  620:extern int printf (const char *__restrict __format, ...);
  1035:  using ::printf;          // namespace std { using ::printf; } из <cstdio>
  ```
- **142 строки-маркера** вида `# 96 "/usr/local/include/c++/14.4.0/cstdio" 3`. Через них компилятор знает, из какого файла и с какой строки пришёл каждый фрагмент, чтобы ошибки и отладочная информация ссылались на исходники, а не на `.i`. Флаг `3` означает системный заголовок: предупреждения в нём подавляются.
- **наш собственный код до `main`**: после маркера `# 3 "simple.cpp"` идут `global_counter`, `MAGIC`, `square`, `sum_of_squares`, `bump_counter`.

Комментарии и директивы `#include`/`#define` из `.i` исчезают, остаётся чистый C++.

**3. Где оказалась строка `"Result: %d, Counter: %d, Magic: %d\n"` и что с ней сделал препроцессор?**

```
1098:    printf("Result: %d, Counter: %d, Magic: %d\n", result, global_counter, MAGIC);
```

Она на своём месте — в теле `main`, в конце файла (строка 1098; для компилятора это по-прежнему строка 21 `simple.cpp` благодаря маркеру). Препроцессор её **не тронул**: строковый литерал — один неделимый токен, внутри него макросы не ищутся, а `%d` и `\n` остаются как есть. Escape-последовательности разбирает уже компилятор. `MAGIC` тоже не заменён: это не макрос, а обычная константа C++, препроцессор о ней ничего не знает.

## Этап 2. Компиляция и оптимизации (`simple.s`)

```bash
g++ -S -masm=intel -O0 simple.cpp -o simple_O0.s
g++ -S -masm=intel -O2 simple.cpp -o simple_O2.s
```

**4. Сравните размеры файлов `-O0` и `-O2`.**

| | `-O0` | `-O2` | во сколько раз |
|---|---|---|---|
| байт | 2247 | 1439 | 1.56 |
| строк | 123 | 76 | 1.62 |
| машинных инструкций (без директив и меток) | 50 | 21 | **≈2.4** |

По размеру файла разница всего ~1.6×, потому что значительную часть обоих файлов занимают одинаковые служебные директивы (`.cfi_*`, `.section`, `.type`, `.size`, `.ident`). Если считать только инструкции, оптимизированный код короче примерно в 2.4 раза.

**5. Какие инструкции используются для умножения в `square:` (`-O0`)?**

```asm
_Z6squarei:
	push	rbp
	mov	rbp, rsp
	mov	DWORD PTR [rbp-4], edi    ; аргумент x из регистра — в стек
	mov	eax, DWORD PTR [rbp-4]    ; и сразу обратно в eax
	imul	eax, eax                  ; x * x
	pop	rbp
	ret                               ; результат в eax
```

Умножает одна инструкция **`imul eax, eax`** (знаковое умножение, двухоперандная форма). Остальное — накладные расходы `-O0`: пролог/эпилог с `rbp` и бесполезная пересылка `x` через стек, которую компилятор без оптимизаций делает для каждой переменной. Метка называется `_Z6squarei`, потому что в C++ имена искажаются (name mangling): `_Z` + длина имени `6` + `square` + тип параметра `i` (int).

**6. Какие регистры передают аргументы в `sum_of_squares`? Как это связано с соглашениями о вызовах?**

```asm
main:
	...
	mov	esi, 4                    ; второй аргумент b
	mov	edi, 3                    ; первый аргумент a
	call	_Z14sum_of_squaresii
	mov	DWORD PTR [rbp-4], eax    ; результат из eax -> result
```

Аргументы передаются в **`edi` (a = 3)** и **`esi` (b = 4)**, результат возвращается в **`eax`**. Это **System V AMD64 ABI** — соглашение о вызовах Linux/macOS на x86-64: первые шесть целочисленных/указательных аргументов идут в `rdi, rsi, rdx, rcx, r8, r9`, возвращаемое значение — в `rax`. Для `int` используются 32-битные половины `edi`, `esi`, `eax`. Благодаря этому соглашению функции, скомпилированные отдельно (и даже разными компиляторами), могут вызывать друг друга.

Вызов `printf` устроен так же:

```asm
	mov	edx, DWORD PTR global_counter[rip]  ; 3-й аргумент
	mov	eax, DWORD PTR [rbp-4]
	mov	ecx, 42                             ; 4-й аргумент — MAGIC уже подставлена числом
	mov	esi, eax                            ; 2-й аргумент — result
	mov	edi, OFFSET FLAT:.LC0               ; 1-й аргумент — адрес строки формата
	mov	eax, 0                              ; для variadic-функций: число векторных регистров (xmm) с аргументами
	call	printf
```

Даже на `-O0` `MAGIC` подставлена как `42`: `const int` с константным инициализатором — это константное выражение, и обращаться к памяти за ним не нужно.

**7. Почему при `-O2` функция `square` «исчезла»?**

В нашем выводе метка `_Z6squarei` в `-O2` **осталась** (3 инструкции: `imul edi, edi / mov eax, edi / ret`). Но из программы она пропала по сути: её больше никто не вызывает. Во всём `simple_O2.s` есть один-единственный `call`, и это `printf`:

```asm
main:                                     ; -O2
	sub	rsp, 8
	mov	eax, DWORD PTR global_counter[rip]
	mov	ecx, 42                   ; MAGIC
	mov	esi, 25                   ; result = 3*3 + 4*4 — посчитано на этапе компиляции
	mov	edi, OFFSET FLAT:.LC0
	lea	edx, [rax+1]              ; bump_counter() встроена: global_counter + 1
	xor	eax, eax
	mov	DWORD PTR global_counter[rip], edx
	call	printf
	xor	eax, eax
	add	rsp, 8
	ret
```

Что сделал оптимизатор:

1. **Встраивание (inlining).** `square` крошечная, поэтому её тело подставлено прямо в `sum_of_squares` (там теперь `imul edi, edi / imul esi, esi / lea eax, [rdi+rsi]`), а `sum_of_squares` и `bump_counter` — в `main`.
2. **Свёртка констант (constant folding / propagation).** Аргументы известны при компиляции (3 и 4), и `3*3 + 4*4` превратилось в готовое число `25`.
3. **Удаление мёртвого кода.** После встраивания вызовов `square` не осталось.

Отдельное тело `square` всё же сохранилось, потому что у функции **внешняя связность** (external linkage): компилятор видит только одну единицу трансляции и не может знать, не вызовет ли её другой `.o`-файл. Если объявить функции `static` (внутренняя связность), их тела удаляются полностью. Проверено (`simple_static.cpp` → `simple_static_O2.s`): ни одного упоминания `square`/`bump` в файле, 40 строк вместо 76, `main` тот же самый. Тот же эффект дают `-flto` и `-fwhole-program`.

## Этап 3. Ассемблирование в объектный файл

```bash
g++ -c simple.cpp -o simple.o
nm simple.o
```
```
000000000000003c T _Z12bump_counterv
000000000000000f T _Z14sum_of_squaresii
0000000000000000 T _Z6squarei
0000000000000000 r _ZL5MAGIC
0000000000000000 B global_counter
0000000000000052 T main
                 U printf
```

`T` — код в `.text`; `B` — `.bss`; `r` — `.rodata`; `U` — неопределённый символ, который подставит компоновщик (`printf` из libc). Адреса в `.o` — это смещения внутри секции, потому что настоящие адреса ещё не назначены.

**8. Почему `MAGIC` имеет тип `R` (read-only data), а не `D` (data)?**

`MAGIC` объявлена как `const`: изменять её нельзя, поэтому компилятор кладёт её в секцию **`.rodata`** (read-only data), а не в `.data`. При загрузке программы `.rodata` отображается в память **без права записи**: попытка записать туда (например, через `const_cast`) вызовет `SIGSEGV`. Кроме того, такие страницы могут разделяться между процессами. В `.data` лежат изменяемые глобальные переменные с ненулевым начальным значением.

Буква у нас **строчная, `r`**, и имя искажено как `_ZL5MAGIC` (`L` — local). Причина в том, что в C++ константа `const` на уровне пространства имён по умолчанию имеет **внутреннюю связность**, как будто она `static`, а `nm` показывает локальные символы строчными буквами. В C или с `extern const int MAGIC = 42;` был бы глобальный символ `R`.

Для сравнения: `global_counter` попала не в `D`, а в **`B` (`.bss`)**, потому что она инициализирована нулём. Нули не нужно хранить в файле, загрузчик просто выделит обнулённую память. Поэтому у `.data` размер 0.

**9. Что показывает `size`? Какие секции самые большие и почему?**

```
$ size simple.o
   text	   data	    bss	    dec	    hex	filename
    347	      0	      4	    351	    15f	simple.o

$ size -A simple.o
section           size
.text              151
.data                0
.bss                 4
.rodata             44
.comment            19
.note.GNU-stack      0
.eh_frame          152
```

`size` показывает размеры секций, сгруппированные по трём классам (формат Berkeley):

- **text** = всё, что только для чтения: `.text` (151) + `.rodata` (44) + `.eh_frame` (152) = **347**;
- **data** = инициализированные изменяемые данные (`.data`) = 0;
- **bss** = неинициализированные/нулевые данные = 4 (`global_counter`);
- **dec/hex** — сумма в десятичной и шестнадцатеричной записи.

Больше всего места занимают:

1. **`.eh_frame` (152 байта)** — таблицы раскрутки стека (DWARF CFI). Для каждой из 5 функций там лежит запись (FDE), описывающая, как восстановить регистры и найти адрес возврата. Это нужно исключениям C++ и отладчикам/профилировщикам. Директивы `.cfi_*` в `.s` — как раз исходник для этих таблиц. Служебные данные здесь больше самого кода.
2. **`.text` (151 байт)** — машинный код пяти функций, собранный с `-O0`, т.е. с прологами/эпилогами и пересылками через стек.
3. **`.rodata` (44 байта)** = `MAGIC` (4 байта) + выравнивание до 8 + строка формата (35 символов + `\0` = 36 байт).

## Этап 4. Компоновка и запуск

```bash
g++ simple.o -o simple
./simple
```

**10. Какой результат вывела программа?**

```
Result: 25, Counter: 1, Magic: 42
```

`sum_of_squares(3, 4) = 9 + 16 = 25`; `bump_counter()` увеличил счётчик с 0 до 1; `MAGIC = 42`. Код возврата 0.

После компоновки `printf` стал `U printf@GLIBC_2.2.5` — его разрешит динамический загрузчик при старте, связав с `libc.so.6`. Символы получили настоящие виртуальные адреса (`main` — `0x401178`, `MAGIC` — `0x402008`). Исполняемый файл весит 15 888 байт против 2048 у `simple.o`: добавились стартовый код (`_start`, `crt*.o`), секции для динамической компоновки (`.dynamic`, `.plt`, `.got`, `.interp`) и заголовки программы ELF.
